## Observe and stop

Does it generate a concrete runtime inline/consolidation/removal/redraw candidate,
with a maintenance-cost reason, while retaining useful semantic/validation/
transaction boundaries? Merely removing a cast is still not that outcome.
Assess exact scope and reasons; a larger candidate is not automatically adopted.
Keep mapping KEEP and the implemented two-forwarder removal unless new evidence
actually changes their value. A2/B2 and Alder remain untouched.

Whether the candidate appears or not, stop after this one application. Preserve
the first negative result. A positive result is a small same-input improvement
consistent with the cue, not causal proof, a success-rate estimate or validation
on unseen subjects. A negative result remains a limit; do not tune and rerun.

## Reproduce

From a repository containing this PR, create a separate checkout at the baseline
above with only baseline ancestry visible. Apply `guidance.patch` there with
`git apply`. Verify that `git diff --name-only` lists only Decision 0016 and that
source/tests are unchanged. Give a fresh agent the previous intake prompt and
that directory. Keep evaluation files outside the input checkout. The manifest
records SHA-256 for the prompt and both baseline/treated Decision, plus patch hash.
Agent answers are stochastic; reproduction fixes inputs, not output identity.
