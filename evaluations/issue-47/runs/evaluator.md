**Prior comparison.** Actual diff `67fc622` moves this same receipt operation from the row body into a private same-file function. The prior inline block gives adjacent retirement context; current code gives an addressable operation but requires returning to its caller for timing and to the outer function for recovery. Diff `10549ce`, supplemented by its parent's 465–525 range, shows the earlier row work was inside `executeTransfer`; the split gives shared finalization and a distinct work function without moving recovery ownership. These are source comparisons, not timed comprehension experiments.

**Resolution and stopping point.** Static source resolves the candidate validation site and supported ordering, once a specific error is known. The vague packet does not uniquely choose UPDATE, DELETE, earlier identity rejection or database failure. It cannot identify the historical stored SQL, returned receipt, Active Black value or actual commit outcome. Need actual error/cause/runId, operation/link, deployed SQL and driver/database state. The existing mutable integration test at 530–590 explicitly authors COMMIT-response loss after server execution and expects succeeded Run state; it was inspected, not run. An exception alone therefore cannot establish rollback. Stop at the code contract and missing evidence; neither a dishonest receipt nor a broken transaction is established.

## C2 — concrete PostgreSQL execution and transaction composition

**Initial packet (authored):** caller reports transfer failure followed by unexpected persistence; no executor construction, transaction trace or database state is supplied.

**Observed navigation and negative finding.** Searching `QueryExecutor` reached `_shared/query-executor.ts`, `adapters/pg/sql-client.ts`, registration workflow and tests. It did **not** identify the execute-transfer transaction implementation: `executeTransfer` takes `TransferExecutionClient`, not `QueryExecutor`. This distinction corrects an ambiguous initial route rather than revealing a defect.

For registration, `QueryExecutor.transaction` is optional; `create-transfer-setting/workflow.ts` requires a function and performs name resolution, parent insertion and links inside its callback. `fromPg` binds Serene SQL and calls the supplied queryable; it does not supply a transaction. `tests/adapters/pg/features.integration.test.ts` supplies a concrete `pg.Client`, begins an outer transaction and adds savepoint/release/rollback behavior. In contrast, the unit fake at registration test lines 130–245 simply invokes `operation(this)`. Both satisfy the callable shape; only one inspected fixture demonstrates intended database composition in source. Neither is evidence of a deployed wiring or a successful test run.

**Prior comparison.** The actual `11b8ce9` diff shows the older adapter constructing an `AshibaPostgresQuerySource` and calling external `preparePostgresQuery` with query-model/optional-compression inputs. Current adapter calls `bind(query.sql, ...)`; `db54426` records the later Serene replacement. Removing the historical preparation surface reduces the local set of binding inputs to inspect, but both paths still delegate transaction policy to their caller. External historical helper internals were not inspected; this is not a semantic-equivalence claim. The unchanged QueryExecutor seam also remains a meaningful alternative to replacing it with direct driver calls: it supplies typed query contracts and fixture substitution, while concrete transaction behavior must still be checked where composed.

**Resolution and stopping point.** Static source uniquely identifies the shipped `fromPg` implementation, not which implementation or callback an application supplied. A method's presence cannot prove atomicity. For transfer execution, use the dedicated-client contract and Run evidence from C1; for registration, obtain the actual executor constructor/callback, connection ownership, transaction trace and durable rows. No production composition was found in the searched `src`, `tests` and README scope. Do not infer an invalid Pool use or a no-op production transaction from permissive types or test fakes.

**Assessment.** Keep the present seam and application transaction responsibility. A concrete diagnostic question becomes explicit: *which caller-provided transaction implementation and connection ran this invocation?* That is a useful application of existing ownership reasoning, not evidence that DI/interfaces/factories should be added or removed. Renaming the interface or collapsing it would not answer the historical question.

## C3 — historical SQL/configuration reconstruction

**Initial packet (authored):** historical Run output differs from expectations; operator asks which SQL/configuration ran. No Run row, actual SQL, deployment or Run ID is supplied.

**Observed navigation.** Search `execution_configuration` led to `setPhaseRunSql`, `loadSetPhase`, Run DDL and integration evidence. `boundary.ts` reads locked Setting/Links, chooses set phase for non-null profile, validates it, and inserts `phase.evidence` during **Run creation**, before committing and beginning work. It re-reads configuration and rejects changes before work. `config.ts` evidence is `{ engine: 'immutable-set-v1', setting, links }`; it contains loaded master SQL, hashes and revisions. `execute.ts` 1–160 follows configured source/identity/evaluation/Red/Black/verification slots and adds stage/Link context to errors. The Run DDL allows null configuration and explicitly describes legacy null behavior.

The legacy row path reads current `source_sql_body`, mapping and generated DML bodies; its application definition includes `resolveLogicalKey`. `runSql` records arguments, setting and status, without capturing those masters or resolver. The pre-set-phase source `ff0cbbd^:.../queries.ts` 1–28 confirms this historical Run shape. This is the relevant prior operational alternative, not a claim the row and set engines support identical semantics. Decision 0013 restricts the opt-in engine to reviewed immutable/text-key behavior; mutable users cannot switch simply for forensic convenience.

**What resolves and what does not.** Static source identifies configuration locations, not historical values. With an actual set-phase Run row, captured master configuration can resolve the selected deployment configuration even if today's masters differ. It does **not** prove any phase ran: creation commits before work, a configuration change can reject work, admission can be empty, and errors roll back work. The inspected integration test at 140–183 checks the engine label; it is not a complete reconstruction test and was not executed.

Even full captured masters do not reconstruct source data, previous destination/Active state, external function/trigger bodies, transaction outcome or all effective invocation options. In particular, work accepts an invocation `maxDirtyKeys` lower than the captured profile cap; `run_arguments` is the user argument object, not an archive of this option. A row-mode Run also depends on the application's resolver and optional metadata-routine deployment. No deployed function bodies, session settings, source snapshots, retained call records or historical database backups were available. Hashes identify text consistency, not semantic approval or executed effects. Stop at configuration provenance; do not label a current SQL difference the root cause or promise deterministic replay.

**Material change in assessment/follow-up.** A change-time review can resolve the current SQL's authoring and binding ownership while leaving the historical question unanswered. This walkthrough materially changes the concrete next question to: *for a specific historical row-mode Run, can existing deployment/caller records recover the exact masters, resolver and invocation options; if not, does an actual support requirement need that recovery?* For set phase, first fetch the captured configuration and distinguish it from execution/result evidence. This is stronger than “find the implementation,” but does not establish a requirement to snapshot every input or extend the schema. Retain both execution modes and existing trust/recovery choices. Whether missing historical evidence justifies any product change is unknown.

## Interpretation and limits

Decision 0016 already explicitly lists incident diagnosis, demands necessary pre/postconditions, effects and recovery ownership, and allows source walkthroughs and navigation improvements without measuring time. Decision 0017 already makes removal conditional and disclaims demonstrated agent-effectiveness gains. Alder Q1 addresses faithful continuation after error, Q2 cause/state distinctions, Q3 handoff guarantees; P1 permits interruption scenarios, P2 returns implementation-selected meaning to Business Design, and S stops unsupported extra requirements. This evaluation found no new business meaning requiring owner approval and no missing universal review rule.

Observed results are the inspected navigation, concrete source/history differences, and absent incident evidence. Predicted investigation costs are the extra caller/history checks needed if these authored situations occur; neither their duration nor incidence was measured. Source hops/LOC do not establish latency, human time, agent speed or reliability. No unprompted control run establishes that the explicit lens caused better findings. C1/C4 are negative results for new structural benefit; C2 exposes ambiguity and composition evidence, not an interface defect. C3 materially changes a local follow-up, yet its general logic is already available under current guidance.

False positives avoided include treating committed success after a lost response as corruption, a callback-shaped transaction as atomicity proof, captured configuration as execution proof, a hash as SQL approval, and current master rows as historical evidence. Requiring DI removal, full tracing, persistent code mappings, complete replay, additional frameworks or recurring audits would overapply the evidence. No runtime or Business Design change follows automatically.

Stop after these four cases. The justified outcome is a bounded Velvet application and follow-up question, with unchanged structural dispositions. Evidence is insufficient to promote a distinct cross-project rule, but sufficient to show this local diagnostic application is useful. No Alder candidate wording is proposed.
