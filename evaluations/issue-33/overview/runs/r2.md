## Overview

The public boundary reexports executeTransfer from main and the error/types from row-work (boundary.ts:1-3). main.ts owns the transaction lifecycle. It rejects invalid metadata mode, limit and arguments before BEGIN (23-41). Inside the first transaction it locks/validates the Setting, selects the legacy or set phase path, validates legacy definition/source-key agreement, source key columns, enabled links and their mapping, then loads set phase configuration if applicable (43-72). Mapping validation is a loaded-value check, not a transaction owner (link-mapping.ts:9-30). Setting SELECT uses FOR UPDATE; links use FOR SHARE ordered by execution_order (queries.ts:3-10).

Only after validation does it insert a running Run, optionally with configuration evidence, and COMMIT it (main.ts:73-79; queries.ts:20-23). It starts a second transaction, reacquires configuration locks and compares complete Setting/link values to the earlier snapshots before dispatching executeSetPhase or executeRowTransfer (80-102). After the delegate returns it marks the Run succeeded and commits, then returns counters (103-105). Thus the coordinator owns Run status and transaction boundaries; delegated work runs inside its second transaction.

On a caught failure it attempts rollback, collecting recovery errors. Only if the initial Run COMMIT resolved and rollback resolved does it open a separate failure-recording transaction, update the Run, and commit. Failure of that recovery causes a further rollback attempt; all errors are retained. A known runId yields TransferExecutionError, otherwise the original error is thrown (106-140). failSql only updates a still-running Run (queries.ts:48-51). A rejected COMMIT response does not establish rollback: initial commit ambiguity leaves runPersisted false even if the server persisted the Run; final commit ambiguity may leave success durable, and the guarded failure update avoids overwriting success. A rollback response after an ambiguous commit does not prove that earlier commit was undone. The initial BEGIN is outside the try.

Inspected complete boundary, main, queries and link-mapping. Row-work execution/error construction, set-phase loader/executor and stored routine bodies are not yet inspected; this overview claims their dispatch ownership, not their internal effects or actual database correctness. Static SQL above establishes intended queries, not observed execution.

## Target

The shared mutable UPDATE/DELETE returned-key check is executeMutableDestination, row-work.ts:363-395, called after Work creation from 253-254. It chooses UPDATE when source exists and DELETE otherwise, requires nonempty stored SQL, rejects reserved parameter collisions, binds the serialized Active Black destination key, requires that binding and (for UPDATE) every mapped column, then executes (370-385). It requires both one returned row and rowCount 1 and projects nonnull destination key columns before deep equality with Active Black (386-394; projection 65-72). Thus this check occurs after a destination statement, not before its possible effects.

The earlier distinct guard is row-work.ts:160-169: an active mutable source row's mapped key must match Active Black before reassessment, even if key columns are excluded from comparison. Reassessment validates exclusion configuration, binds the reserved active key, requires one pair of JSON texts, and uses compareSql to validate column sets and compare JSONB after exclusions (170-206; queries.ts:53-62). A no-change result skips execution. Initial no-op covers absent source/active or insert-only with active; duplicates override the skip reason (159,208).

Work fields encode the decision before effects (217-250). A routine skip delegates Work plus Processing to record_skipped; non-skips create ordinary Work in both modes. Mutable physical deletion must pass the shared destination checks before retirement (253-264). Row retirement clears matching Work active references, deletes matching Active Black and requires one returned row (397-411; queries.ts:63-64,71-73). Routine retirement calls retire_active with withLineage false. Mutable update retains Active Black and creates no lineage. Processing follows successful path completion unless already recorded by a metadata routine (357-358). Metadata stored routine internals are not exposed by their local SQL wrappers and have not been inspected; exact internal parity is uncertain.

No mutable helper commits or recovers; failures propagate to executeTransfer (row-work.ts:75-77), whose rollback/failure recording and ambiguous-COMMIT limits are described above (main.ts:106-140). The error class carries runId, cause and recoveryErrors (row-work.ts:25-33). Stored destination SQL can already have run when a returned-key mismatch throws; recovery is transaction-level, not a helper compensation. Actual SQL effects and rollback success cannot be inferred solely from source guards.

## Broad

Preparation and identity: executeTransfer validates and commits the running Run before re-locking and dispatching the legacy body; its exact success/recovery ordering remains as recorded in Overview. executeRowTransfer selects pending eligible dirty/link pairs, optionally limiting whole distinct Dirty Keys before expanding eligible links (row-work.ts:104-112; queries.ts:11-19,80-99). Succeeded/skipped Processing excludes pairs; there is no watermark. It resolves all logical keys from shallow-frozen copies of dirty JSON, verifies exact key-column names/non-null values, canonicalizes JSON and only then queries current source values once if work exists (113-125). keyText sorts object keys, accepts finite numbers and JSON-compatible primitive/array/plain-object values; SHA-256 hashes canonical text (40-63). Source rows are indexed by projected key, with duplicate logical source keys rejected (126-131). The resolver and developer source SQL internals remain outside inspection.

Decision ordering: each item obtains its link, model and current source, then determines duplicate context by link plus canonical key. Duplicate items skip the active lookup and mapping; other items lock Active Black by link/key and map current source columns, rejecting missing/undefined mapping inputs (135-158; queries.ts:24-25). Mapping happens even for an insert-only active no-op if source exists. Absent source and active, or insert-only with active, initializes no-op (159). Active plus current non-insert-only work runs mapped mutable-key guard first, then reassessment, JSONB validation and comparison (160-206). Exclusions are constrained to allowed columns; compareSql requires object JSON, required nonexcluded columns and no unknown columns, and compares values after exclusions (queries.ts:53-62). Duplicate gets duplicate_ignore ahead of no_op (208). These facts mean validation may fail before Work, and reassessment may issue SQL before Work; I do not assume that developer-authored reassessment SQL is effect-free.

Work and effects: common identity, route flags, evaluated active key, and result are assembled before a Work is persisted (209-250). Routine skipped work calls record_skipped and marks Processing recorded; other work calls workSql. Non-skips with active mutable state execute and validate UPDATE/DELETE before any retirement (253-264,363-395), as detailed in Target. Update retains active state; delete retires without lineage. Row retirement clears Work references then deletes Active Black and checks exactly one returned row (397-411). Routine retirement is a single retire_active call whose internal body is unavailable locally.

For immutable active state, the code checks/binds Red SQL to every original key column, executes, requires one returned row and rowCount 1, projects a nonnull key and requires it differ from the original (266-280). It constructs Red lineage using the old destination key as source identity, then retires Active Black and records Red lineage: row mode explicitly retires before lineage, routine mode delegates both with withLineage true (281-302; queries.ts:65-69,78). If source remains, the subsequent Black insert follows Red retirement; if source is absent, there is no replacement insert.

Black insertion applies when source exists and either the model is not mutable or no active exists (304). Stored SQL must consume all mapped parameters; the result must contain exactly one row with rowCount 1 and destination key matching the configured source-to-destination key mapping (305-320). Routine mode invokes record_black with result/work/destination fields and withLineage = !mutable, then marks Processing recorded (322-333). Row mode inserts Active Black, then writes Black lineage only for nonmutable models (334-352; queries.ts:34-41). insert_only therefore gains lineage on its initial insert but existing-active skips. inserted counts Black inserts only, not UPDATE/DELETE/Red. skipped increments for skip routes. completed.add occurs after effects/counters and before fallback Processing; errors in Processing still propagate out and terminate the run (354-360). Fallback Processing covers ordinary row paths and routine paths not handled by record_skipped/record_black (queries.ts:42-45,75-78).

Binding and metadata ownership: main's query helper uses Serene bind in indexed mode for local static SQL (main.ts:35-38). Stored statements use bindStoredSql, including source through storedArguments (row-work.ts:414-417). The binder lexically skips quoted strings/identifiers, E-string escapes, line comments, nested block comments and dollar quotes; it rejects unterminated quotes/comments, executable positional $n markers and named values missing an own data descriptor or undefined value. It permits extra context by copying only referenced names to a null-prototype object, then delegates marker lowering/value construction to bindExternal/externalSql (trusted-sql.ts:1-77). It does not approve stored SQL semantics. Link mapping checks mapping object/nonempty entries, allowed targets/nonempty source names, exact source-key order and matching destination key names/mapping correspondence before Run creation (link-mapping.ts:10-30). SQL wrappers reveal metadata call arguments but not record_skipped/record_black/retire_active internal ordering or checks. Their deployment file is outside the advertised local source list, and I did not access it.

Completion and recovery: only after the entire row loop returns does main update Run succeeded and COMMIT. All row/helper errors propagate to main; rollback and conditional separate failure transaction preserve recovery errors. The failure update is restricted to running status, so a success already committed before a lost response is not rewritten failed. Initial-commit ambiguity can leave a durable running Run without attempted failure update. These are code-path observations, not proof of the server's final transaction state.
