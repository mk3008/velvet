## Overview

`executeTransfer` owns the transactions on an idle dedicated client (boundary.ts:72-203). Before BEGIN it validates metadata mode, positive safe maxDirtyKeys, and argument object shape (85-100). The initial BEGIN is outside its try. Within the first transaction it locks and validates the Setting, legacy definition/source-key agreement where applicable, source key uniqueness, and enabled links; checks mutable date controls, stored insert presence and mapping; optionally loads set configuration; then inserts a running Run (103-139). Setting uses FOR UPDATE; links are ordered and share-locked (queries.ts:3-10). Run insertion SQL is at queries.ts:20-23.

It commits Run creation, sets runPersisted only after the commit resolves, starts a second transaction, reacquires configuration and checks deep equality (140-149). It dispatches either set-phase execution or the legacy row/routine worker (150-164). The latter prepares pending identity/source rows, makes per-link decisions, records Work, performs destination and metadata effects, and records Processing (233-489). It does not commit or recover. The coordinator marks Run succeeded then commits and returns counters (165-167; queries.ts:46-47).

On an error inside the try, the coordinator attempts rollback. Only if Run persistence was acknowledged and rollback resolves does it open a failure-recording transaction, update the still-running Run, and commit. Failure of recovery is accumulated, with another cleanup rollback attempted. A known runId yields TransferExecutionError carrying cause and recoveryErrors; otherwise original error propagates (168-201). The failure UPDATE explicitly requires run_status='running' (queries.ts:48-51), so an ambiguously acknowledged successful work commit is not overwritten as failed. A rejected commit response does not establish rollback: initial commit rejection can leave a persisted Run while runPersisted remains false; work-commit rejection can leave committed success. Successful rollback response alone cannot resolve that historical ambiguity.

Inspected complete boundary.ts and queries.ts. Set-phase internals, link-validation implementation, stored binding implementation and external metadata-routine bodies remain uninspected at this stage. Stored source/reassessment/transfer SQL executes through the client; its correctness and actual database outcomes are not established by this reading.

## Target

Returned-key checks for mutable UPDATE and DELETE are in executeMutableDestination, boundary.ts:492-524, specifically 514-523. After executing stored SQL it requires both one returned row and rowCount=1, then projects destination key columns (projection rejects missing/undefined/null keys at 62-69) and deep-compares them with Active Black's destination_key_json. The SQL effect precedes this validation; failure throws to the caller, not a local rollback. Both modes call this identical helper at 383.

Earlier, for active plus source row and a non-insert-only model, the mutable mapped key is checked at 290-298, before reassessment and before Work. It prevents identity changes even when key columns are excluded from comparison. Reassessment validates exclusions and a reserved parameter, requires binding the active key, executes stored SQL, checks a single pair of JSON texts, then runs compareSql to establish valid comparison and changed/no-op (299-335; queries.ts:53-62). Duplicate or no-op determines skip, and only then are Work fields recorded (337-379). Consequently these earlier failures have no Work for that item; returned-key failures occur after Work and destination execution.

For active mutable source absence, successful DELETE validation is followed by retirement (384-392). Routine mode invokes retire_active with withLineage=false; row mode clears Work references, deletes Active Black by active id and link, and requires exactly one returned retirement row (527-540; queries.ts:63-64,71-78). UPDATE does not retire Active Black. Routine skip uses record_skipped for Work/Processing; non-skip mutable UPDATE/DELETE uses ordinary Work and the final Processing insertion (374-380,486-487). This describes caller intent for routine metadata; external routine bodies were not available in the listed local packet and have not been verified.

Recovery remains solely executeTransfer's rollback/conditional failed-Run transaction, with commit ambiguity and accumulated recovery errors as explained in Overview (168-201; queries.ts:48-51). The helper validates the returned evidence, not that arbitrary developer SQL affected only the intended row; actual SQL semantics and DB execution remain outside the inspection.

## Broad

Inspection covers every local legacy execution body in boundary.ts (complete file read during Overview), all its local metadata query definitions in queries.ts, mapping validation, and stored binding. This review relies on those prior reads as well as the two Broad-stage whole-file reads below.

Preparation and identity: coordinator pre-Run checks and transaction ownership are described above. Mapping validation (link-mapping.ts:10-30) requires a nonempty object, known destination column targets and nonempty string sources, exact ordered sourceKey agreement, nonempty destinationKey whose sorted names equal destination_key_columns, and destination key mappings agreeing with column mapping. Pending selection filters already succeeded/skipped link processing and orders Dirty Key id then link execution order (queries.ts:11-19); bounded selection limits distinct eligible Dirty Keys first, then includes all eligible links (80-99), without a persistent watermark. Worker resolves each explicit logical identity from a shallow-frozen copy before reading source current values, validates exact logical key column names/non-null projection, and canonicalizes JSON by recursively sorting object keys (boundary.ts:36-69,233-249). It executes source SQL only for nonempty work, checks a rowset, projects source keys and rejects duplicate logical identities (250-260). Application resolver and developer source SQL semantics are external assumptions.

Decisions precede Work: for each pending item it determines the model, looks up the source row, and uses link plus canonical key as duplicate context. A completed duplicate bypasses Active lookup and mapping; others select Active FOR UPDATE and map required present/non-undefined source properties (264-287; queries.ts:24-25). No source and no Active is no-op; insert-only with Active is no-op (288). Mapping is still constructed first for a nonduplicate existing source, including insert-only items. Mutable mapped-key stability, comparison validation, reserved-key binding, and reassessment occur before Work as detailed in Target. compareSql requires JSON objects, required non-excluded columns, no unknown columns, and tests difference after excluding columns (queries.ts:53-62). Duplicate skip wins over no-op. Work fields include identity, route, source existence, effect flags, active id and evaluated destination key (337-379). Routine skips use record_skipped and suppress later Processing; other cases insert ordinary Work. This is a meaningful ordering fact: a reassessment failure happens before Work, but mutable/Red/Black transfer failures happen after it in the same transaction.

Mutable effects: active mutable items execute checked UPDATE with a source row or DELETE without it. Helper binding requires the reserved Active key, and UPDATE must consume every mapped column; execution must return exactly one row/count with unchanged destination key (492-524). DELETE then retires metadata, UPDATE keeps Active. Row retirement clears references from all matching Work items, deletes Active, and checks one deleted row (527-540; queries.ts:63-64,71-73); routine retirement passes withLineage=false. Mutable without Active and with source follows Black insertion below. Mutable paths produce no Lineage here.

Immutable effects: active immutable non-skips require Red SQL, bind original destination key columns, execute, require exactly one returned row/count and a different projected key (395-409). They construct Red lineage using original destination identity as source and returned Red identity as destination. Routine retirement receives lineage fields and withLineage=true; row mode retires Active first and then records Red lineage (410-431; queries.ts:65-69). Only afterward, if source exists, does Black insertion occur. Source absence leaves Red-only retirement.

Black effects: any non-skip source row with no active mutable update executes stored insert using mapped values. All mapped columns must be consumed. The returned row/count must both be one and projected destination key must equal destination_key_mapping values taken from source (433-449). Routine mode calls record_black with result/work/destination fields and withLineage=!mutable, then considers Processing recorded (451-462). Row mode inserts Active then records Black lineage for nonmutable models (463-481; queries.ts:34-41). This includes insert-only Black lineage. inserted increments only after these metadata calls, so it counts Black inserts, not mutable updates or Red inserts.

Completion: skips increment skipped; all completed items add their duplicate context, then insert Processing unless a routine call was treated as having recorded it (483-487). Consequently an exception in Processing aborts the worker before any later item. Work, destination effects, Active/Lineage and Processing all run inside the coordinator's second transaction; worker returns counters only after the loop. Coordinator marks succeeded and commits; rollback/recovery belongs only to it, subject to the acknowledged-commit caveats in Overview.

Binding: authored query constants use Serene bind with indexed parameters (boundary.ts:97-100). Stored binding scans past quoted strings/identifiers, escaped strings, line comments, nested block comments and dollar quotes; it rejects unterminated constructs, positional markers outside those regions, and missing, accessor-only or undefined named parameters. Cast syntax is not a parameter. Only discovered own data values are passed to externalSql/bindExternal; extra context is permitted (trusted-sql.ts:7-76). This is parameter/authoring validation, not SQL authorization or semantic proof. Serene internals were not inspected.
