## Overview

`executeTransfer` owns transactions, Run creation/finalization and recovery; the legacy `executeRowTransfer` owns ordered work within its caller's transaction and propagates errors (boundary.ts:72–203,204–232). Input metadata mode, dirty-key limit and argument shape are checked before BEGIN (85–103). Inside the first transaction it locks and validates the Setting, chooses set-phase or legacy configuration, validates source identity and enabled links, loads set-phase configuration if selected, and inserts a running Run (105–139). Setting SELECT is FOR UPDATE and link/definition SELECT takes shared locks ordered by execution_order (queries.ts:3–10). Run SQL inserts running status (20–23).

The first COMMIT is awaited before runPersisted becomes true. It then begins a separate execution transaction, reacquires configuration locks and requires deep equality with the original setting/links before dispatching set-phase or legacy execution (boundary.ts:140–164). The legacy path prepares pending identities/source rows, processes each work item, makes decisions before Work creation, performs destination/metadata effects, and records Processing (233–489). Success updates Run to succeeded then commits the execution transaction and returns counters (165–167; queries.ts:46–47).

On an error caught after the first BEGIN, coordinator attempts rollback. Only if Run commit was acknowledged and rollback succeeded does it start a failure-recording transaction, conditionally update the still-running Run to failed, and commit. Failure-recording failures collect recovery errors and trigger a cleanup rollback. With an assigned runId it throws TransferExecutionError preserving cause and recovery errors; otherwise original error is thrown (168–201). Initial BEGIN itself is outside the try. A rejected COMMIT response is ambiguous: the server may have committed; failSql only changes running Runs, protecting an already-succeeded Run (queries.ts:48–51). An unacknowledged first commit leaves runPersisted false even if the server persisted it. Successful rollback response likewise does not prove an earlier commit was undone.

Inspected complete boundary.ts and relevant coordinator query ranges. Set-phase internals, link-mapping and stored-SQL binding bodies, most metadata SQL and actual developer-authored SQL/DB behavior are uninspected at this stage; owner and ordering statements for those are call-site facts, not proof of leaf implementation or server effects.

## Target

Mutable UPDATE/DELETE returned-key checks are in executeMutableDestination (boundary.ts:492–524), shared by row and routine modes via 382–383. It selects Update when source row exists and Delete otherwise; checks stored statement presence, reserved-parameter collision, Active Black key binding, and (Update only) consumption of every mapped column (499–513). After executing SQL, it demands both one returned row and rowCount 1, projects all destination key columns (projection rejects absent/null/undefined at 62–69), and requires deep equality with Active Black's destination_key_json (514–523). These are post-effect returned-data checks, not pre-execution proof that the SQL targeted the right row.

Earlier, mapped values are collected from source columns (278–287). For active+source non-insert-only work, mutable mapped destination identity must match Active Black BEFORE reassessment, irrespective of comparison exclusions (289–298). Exclusions are validated; reassessment must bind the reserved active key and return one pair of strings; compareSql verifies JSON objects, required included columns and absence of undeclared columns, then compares after removing exclusions (299–335; queries.ts:53–62). noOp becomes !changed. Source absent+no active and insert-only+active start as no-ops; duplicate wins skip classification (288,337). Work is inserted only after these decisions (338–379), before mutable execution. Routine skip calls record_skipped instead of ordinary workSql; ordinary effectful work still creates Work first.

After successful mutable helper return, DELETE alone retires active metadata (384–393). Row mode clears Work active references, deletes Active Black scoped to active ID and link, and requires one returned deletion (527–540; queries.ts:63–64,71–73). Routine mode calls retire_active with withLineage=false (385–389; queries.ts:78); routine internals are not exposed in the local file list and have not been inspected. UPDATE keeps Active Black. Both modes eventually record Processing at 486–487 unless a routine already recorded it. Returned-key mismatch prevents subsequent retirement/Processing and propagates to coordinator recovery (168–201), which owns rollback and failure recording; the helper and legacy executor do not commit or recover.

Uncertainties: actual stored Update/Delete/reassessment SQL and DB execution, deployed routine bodies and transaction commit outcome cannot be established from these call sites. Routine behavior beyond the call and supplied flags is an intended contract, not inspected implementation. No target-stage boundary reread was necessary because its full text was retained from overview.

## Broad

Preparation and source identity: coordinator validation/transaction ordering is as in Overview. The now-inspected mapping validator requires nonempty mapping with valid destination column names and nonempty string source names, exact source-key array identity, destination-key names matching declared columns, and destination-key source columns agreeing with mapping (link-mapping.ts:10–30). Pending selection admits eligible dirty/link pairs not already succeeded/skipped, ordered by dirty ID and link execution order (queries.ts:11–19). Bounded selection first limits whole dirty keys having eligible links, then expands all their eligible links; no durable watermark is used (80–99). Legacy execution resolves all pending logical identities from frozen shallow copies before source SQL, verifies exactly the setting key columns and nonnull key values, and canonicalizes keys (boundary.ts:233–249,39–69). Source SQL executes once only when work exists; its rowset must be an array, every key must project successfully, and duplicate logical keys throw before any Work (250–260). All returned source rows are checked, not only pending keys.

Duplicate/insert-only/no-op and comparison: each item looks up link/model and current source, then forms a link+logical-key context. Previously completed contexts skip Active lookup and mapping. Other items lock Active Black by link and source JSON key (264–287; queries.ts:24–25). Mapping requires each mapped source property to exist and not be undefined, though null is allowed here. A missing source with missing Active or insert-only with Active is a no-op (288). Insert-only existing rows are nevertheless mapped first, so missing mapping input can throw before its skip. Active+row non-insert-only work performs the early mutable key guard and stored reassessment described in Target (289–335). Duplicate status overrides no-op (337). Comparison SQL validates required included fields, object shapes and allowed column names, compares JSONB values with exclusions removed; malformed JSON may fail in the DB cast (queries.ts:53–62).

Work and mutable effects: common identities, hashes, model/route/effect flags, active/evaluated identity and result labels are assembled before Work creation (338–373). Every ordinary item gets workSql, while a routine skip calls record_skipped with merged Work/result fields and treats Processing as recorded (374–380). Non-skipped active mutable work then calls the shared mutable helper, which validates returned row/key after SQL execution; deletion then retires Active without Lineage, update preserves it (381–394,492–540). Mutable new-source insertion enters the Black branch instead. There is no local transaction inside these helpers.

Immutable Red/Black/Lineage: an active immutable item first requires Red SQL, binds original destination-key values and checks every original key name was consumed. Red execution must return exactly one affected/returned row, project a complete key and produce a different key than original (395–409). Red metadata uses original destination key as source identity and returned Red key as destination (410–422). Routine mode calls retire_active with lineage=true; row mode releases Work references, deletes Active with one-row check, then writes red Lineage (423–431; queries.ts:63–73). If source exists, Black insertion follows Red retirement; absent source stops after Red. Black insertion requires consumption of every mapped column, one affected/returned row, and returned destination-key equality with key mapping projected from the source row (433–449). Routine record_black receives result/work/destination fields and lineage=!mutable, then marks Processing recorded. Row mode inserts Active, then Black Lineage for nonmutable models (450–482; queries.ts:34–41,77). Thus insert-only new rows also receive Black Lineage. inserted counts successful Black insert branches only; updates/deletes/Red-only operations do not increment it (483).

Completion/Processing: skipped increments only for skip branches. completed.add occurs after effect/metadata branches and before ordinary Processing insertion. Routine skips and Black metadata paths suppress the separate Processing query; updates, deletes and Red-only routine paths still use it (485–487). A thrown error stops iteration; completed and counters are only in-memory. Processing stores per-dirty/link result/status and drives future pending exclusion (queries.ts:42–45,11–19). After the executor returns, only the coordinator marks success and commits; recovery and commit uncertainty remain exactly as documented in Overview.

Binding: application-owned SQL uses Serene bind indexed and returns query rows (boundary.ts:97–100). Stored SQL goes through bindStoredSql; its scanner skips SQL quotes (including E-string escapes), line comments, nested block comments and dollar quotes, rejects unterminated constructs and positional parameters, recognizes named parameters outside casts, and accepts only own defined data properties (trusted-sql.ts:7–75). It then delegates marker lowering/value-array construction to Serene bindExternal/externalSql (76). Extra context values need not be consumed by the binder itself; call sites add effect-specific consumption checks. This does not establish correctness of stored SQL or external Serene implementation.
