## Overview

The public entry boundary.ts:1 exports executeTransfer from main.ts (the error and types come from row-work.ts). main.ts owns transactions and recovery. It validates metadata mode, maxDirtyKeys, and argument object before BEGIN (23–41); that initial BEGIN is outside its try. In the first transaction it locks Setting, checks enabled state, chooses set-phase versus legacy definition requirements, validates source identity/key shape, loads enabled links and validates model/mapping/insert prerequisites (43–72). The actual mapping-validator and set-phase bodies are not yet inspected. queries.ts:3–10 shows Setting FOR UPDATE and ordered link/definition FOR SHARE reads. It inserts a running Run (main:73–77; queries:20–23), commits, and only after a fulfilled commit sets runPersisted=true (78–79).

It starts a second transaction, reacquires configuration locks and rejects any deep change in Setting/enabled links (80–87), then dispatches either executeSetPhase or executeRowTransfer (88–102). The legacy worker owns preparation, decision/effect ordering, and per-item metadata, not transactions: it selects pending work, resolves logical identities before executing source SQL, maps/comparisons and decides skip/effects, creates Work before destination effects, then records Processing (row-work:104–360). I read that complete worker, including its mutable and retirement helpers. Routine-mode calls delegate metadata to DB functions; their bodies are not yet inspected. Success updates Run succeeded in the work transaction then commits before returning counters (main:103–105; queries:46–47).

Any caught failure attempts rollback and records rollback errors. Only when Run persistence was acknowledged AND rollback fulfilled does it start a new transaction to mark that Run failed and commit; failures there trigger cleanup rollback and join recoveryErrors (main:106–131). failSql only updates a running Run (queries:48–51), so an ambiguously acknowledged work commit that actually succeeded is not overwritten as failed. A rejected commit response does not prove rollback: even a fulfilled subsequent rollback does not establish that earlier commit failed. An ambiguous first commit leaves runPersisted false and therefore skips failure recording even if a Run became durable. If a runId exists, TransferExecutionError contains it, the cause, and recoveryErrors; otherwise original error escapes (main:132–139; row-work:25–33). No guarantees of actual DB effects, connection usability, or developer-authored stored SQL correctness follow from this code reading. Set-phase internals, binding implementation and mapping validator remain uninspected at this stage.

## Target

Mutable UPDATE/DELETE returned-key validation is in executeMutableDestination, row-work.ts:385–394: after executing the selected stored statement it requires exactly one returned row AND rowCount=1, then projects destination_key_columns (projection rejects missing/null/undefined at 65–72) and deep-compares to Active Black's destination_key_json. Operation choice is based on source row presence (370–374). Both statements must bind reserved velvet_active_destination_key, supplied as canonical JSON; UPDATE must bind every mapped column; reserved mapped-name collisions fail (375–384).

This is separate from the earlier pre-effect mapped-key guard at 160–169: when active+source exist and the model is mutable, mapped destination identity must already equal Active Black, even if key columns are excluded from comparison. Only then are exclusions validated, stored reassessment required/bound, its one pair of string JSON results checked, and compareSql used to determine noOp (170–206; queries.ts:53–62). Thus no-op reassessment cannot conceal a mapped-key change. Source-absent active mutable work has no mapped-key/reassessment branch and takes DELETE; source-absent with no active is no-op. Duplicate/insert-only rules precede these decisions (row-work:142–160,208).

Work metadata is created after those decisions and before destination execution (217–254), so reassessment/earlier guard failures precede Work; returned-key failures occur after Work and destination statement execution. Both row and routine modes call the same mutable helper (253–254). Only successful DELETE validation proceeds to retirement (255–264): routine calls retire_active with withLineage=false; row mode clears Work references then deletes the Active Black by id+link and requires one returned deletion (398–411; queries:63–64,71–78). UPDATE retains Active Black. Successful mutable operations eventually record Processing at 357–358; mutable insertion is a distinct Black path (304–355). Skipped routine mode combines metadata through record_skipped; other routine Black insert uses record_black (245–251,322–333).

The worker throws without catching, committing, or recovering (75–77). main.ts:106–139 owns rollback and conditional separate failure-recording transaction as described in overview. Returned-key failure does not itself undo effects; the coordinator attempts recovery. SQL/DB behavior remains unverified. The available-file list has no deployed execute-transfer-metadata.sql body, so the internal ordering and guarantees of record_skipped/record_black/retire_active remain uncertain; local call ordering and row-mode metadata SQL were inspected.

## Broad

Inspected all available local legacy execution bodies: main.ts, full row-work.ts including its helpers, queries.ts, link-mapping.ts, and trusted-sql.ts. The coordinator ordering/recovery is as in overview; mapping validation is now inspected, not assumed. link-mapping.ts:10–30 validates nonempty mapping, allowed target names/nonempty source names, exact sourceKey order, destination key names against destination_key_columns, and each key's mapping source. This runs under configuration locks before Run creation (main:65–73); it does not itself query or mutate.

Preparation/source identity: pendingSql enumerates unprocessed enabled link × matching schema/table Dirty Keys, ordered by dirty ID and link execution_order; only succeeded/skipped Processing excludes pairs (queries:11–19). boundedPendingSql first admits up to maximum whole Dirty Keys with some eligible link, then returns all their eligible links, with no durable watermark (80–99). The worker resolves all pending logical keys from shallow-frozen Dirty Key copies, requires exact key field names/non-null values, canonicalizes sorted JSON-compatible structures, and hashes keys with SHA-256 for metadata (row-work:40–73,104–120,209–216). It executes stored source SQL only if work exists, validates rowset shape, projects source keys and rejects duplicates before entering per-item effects (121–131). Source is a single collected snapshot in this code, not refreshed per item. Application resolveLogicalKey and stored source SQL semantics are outside the inspected source packet.

Decision ordering: completed is an in-memory set keyed by link+logical key. Duplicate contexts skip Active lookup and mapping. Other items lock Active Black (queries:24–25), then map source values (missing/undefined fails; null nonkey values are allowed), before deciding no-op (row-work:134–160). Thus an insert-only item with Active can still fail mapping validation before being skipped. Absent source+absent active, or insert-only+active, is no-op. Active+present non-insert-only items run the stable mutable mapped-key guard, exclusion validation and stored reassessment before deciding change (160–207). compareSql requires JSON objects, required compared keys, no unknown keys, then tests distinctness after excluding columns (queries:53–62). Duplicate wins over no-op in the recorded skip reason (208). These are source facts, not claims about stored SQL correctness.

Work/effects: workFields/resultFields capture source/model/route, required effects, Active ID and evaluated destination key; Work is inserted only after decision and before destination mutation (217–250). Routine skipped metadata delegates Work+Processing to record_skipped, as implied by its local use and processingRecorded flag, but its DB body is unavailable. Mutable active UPDATE/DELETE use the shared helper and returned-key checks detailed in target. Successful DELETE retires Active; UPDATE keeps it and creates no Lineage. Row retirement clears all matching Work active references, then deletes Active and checks exactly one returned row (398–411; queries:63–73). Routine retirement delegates withLineage=false.

Immutable active work first requires and executes Red SQL bound to every original destination key column. It requires exactly one returned/affected row, non-null projected keys and a Red key different from original (266–282). Metadata uses the original destination identity as Red Lineage source and the returned key as destination (283–293). Then row mode retires Active and writes Red Lineage; routine mode delegates retire_active withLineage=true (294–302; queries:65–78). When source is present, Black insertion follows Red retirement; absent source ends after Red. Black insertion also handles new mutable and insert-only rows. It requires every mapped column be consumed, exactly one returned/affected row, and projected key equal the configured source-derived expected destination key (304–320). Row mode inserts Active then writes Black Lineage only for nonmutable; routine mode calls record_black with withLineage=!mutable and marks Processing recorded (321–353). inserted counts successful Black inserts, not mutable updates or Reds (354).

Completion: skips increment skipped; every successfully handled context is added to completed, then standalone Processing is inserted unless routine skip/Black already recorded it (356–359). Processing failure still aborts the worker; completed is only local state and no returned success follows. Routine active mutable update/delete and immutable Red-only paths fall through to standalone Processing. Row metadata SQL explicitly writes work linkage and succeeded/skipped result (queries:42–45). Whole-worker completion returns counters to main, which marks Run succeeded and commits. No per-item commit/catch exists. Recovery, including failed-Run status guard and ambiguous commits, is owned by main as explained in overview; it is attempted recovery, not proof effects were undone.

Binding: main.ts:35–38 binds local Sql via Serene indexed parameters. row-work.ts:414–417 adapts bindStoredSql for source execution. trusted-sql.ts:7–76 lexes quoted strings/identifiers (including E-string escapes), comments with nested block handling, dollar quotes, skips PostgreSQL casts, rejects positional $n outside those forms, and requires named parameters to be own defined data properties. Only encountered values pass to externalSql/bindExternal; extra context is allowed. Serene's implementation is not available/inspected, and binding does not approve developer SQL.
