# Independent evidence review: overview navigation extension

Reviewed against the frozen baseline `0086480a3c528d1d2a52d49056d90616234f5a38`. This is an independent evidence review, not an additional scored participant run or a production Alder/runtime review. I read repository guidance, Decision 0016, the frozen protocol and participant instructions, fixtures, reader/parity/summary implementation, launch record, all four staged answers and all reader logs. The author had not supplied a preferred conclusion.

**Recommendation: keep the exact three-file candidate experimental; do not adopt it into runtime on this evidence.** There is a concrete, reproducible *option* to read the coordinator without row details, and one participant used it successfully. That does not establish reproducible net maintenance benefit after accounting for the facade, exported internals, additional navigation and complete-review obligations. This is not ADOPT blocked only on tests or timing. For the current bounded runtime comparison, keep is favored; retain the fixture as evidence, with no planned execution or recurring experiment. B2's adopted same-file helper and A2's distinct DEFER are unaffected.

## Coverage and deterministic checks

I executed `summarize.mjs` and compared its parsed output with the retained measurements using strict deep equality. Every logged command was replayed against the assigned frozen source, including exposure arrays, UTF-8 output bytes and output SHA-256; the outputs matched. I also executed `parity.mjs --typecheck`; its complete parsed output exactly matched retained parity.json. Typecheck used the script's temporary src/tests copy under tmp; no logs, measurements, fixtures or runtime source were edited.

The replay confirms all 13 local declarations were fully exposed cumulatively in every run: Row, TransferExecutionClient, TransferExecutionDefinition, TransferExecutionError, object, keyText, hash, projection, executeTransfer, executeRowTransfer, executeMutableDestination, retireRowActive and storedArguments. That is 525 declaration lines per run. All runs additionally exposed the complete queries.ts (99), link-mapping.ts (31), and trusted-sql.ts (77) by Broad. Thus no reported cumulative saving is produced by leaving an execution helper or required binding/metadata wrapper unread. Shared modules are pinned, and the parity check verifies the six shared local modules against the baseline revision.

Parity establishes byte-identical baseline and exact declaration text relocation after stripping the added export modifier, with no added/duplicate declaration and explicitly checked imports/reexports. `getText` excludes leading trivia, so its equality claim should not be described as proving every leading comment byte identical; the fixture's executable declaration bodies and signatures are covered. It does not establish runtime module initialization, PostgreSQL behavior, or baseline semantic correctness. The type-inclusive cycle lengthens through main; it is not a new runtime cycle.

r2 demonstrates a useful bounded walkthrough: boundary's exports lead to main, the coordinator stays visible, queries establish lock/status SQL, and mapping is inspected without opening row execution. The 274 overview lines include 31 mapping lines which the other overview readers did not inspect, so this is not an identical leaf-coverage comparison, although all satisfy the frozen overview requirements. The candidate overview's zero row detail is real for that route.

r4 followed the same entry into the complete worker during Overview, exposing all 367 row-detail lines and 660 total unique lines. Both baselines chose a whole-boundary overview despite arbitrary search/range access. Therefore the candidate did not consistently induce a focused overview, and this sample does not show whether ordinary baseline coordinator ranges would erase most of the observed r2 advantage. It would be wrong either to call the benefit universal or to conclude that no reader can benefit: r2 is a concrete counterexample to the latter.

The deeper boundary problem reappears in r2's Target: it reads all 417 lines of row-work, including 90 narrowly classified immutable-Red/Black lines unrelated to locating mutable checks. The other participants already had the worker in context and used limited rereads or queries. Small target counts for them do not show less total acquisition: r1/r4 add no new lines, and r3 adds only the 32 previously unseen query lines. Broad adds only 77 lines for r2 because mapping was already read, versus 108 for the others. No further recursive extraction is justified by this experiment; a new split would have its own seam and ownership costs and is not the frozen candidate.

By the full local task, baseline totals are 753 and candidate totals 768: identical execution content and common dependencies plus 15 additional layout/scaffolding lines. This is evidence of unchanged broad inspection obligations, not proof that 15 lines materially harm maintenance. File transitions include search-output path changes and across-stage transitions; they are exposure-path switches, not measured human navigation time or runtime calls.

The exact candidate adds main.ts and row-work.ts and converts boundary into a three-line compatibility facade. Its main file is 141 lines and row-work is 417. Public exports remain reachable through the old boundary, but object and executeRowTransfer become internal runtime exports and Row a type export. The existing eleven-field row-worker argument object remains unchanged; there are no extra function calls or duplicated declarations. Imports split across modules and public error/types reside with row work, adding paths to inspect even for a main-oriented reader. These are modest, concrete costs, not evidence of a catastrophic interface. The benefit must nevertheless exceed them; file brevity alone does not establish that balance.

## Limits and decision

Four procedurally isolated same-model contexts, two per variant, provide descriptive cases rather than a population estimate. File names reveal layout. Whole-file strategy varies; stage order intentionally carries information forward; no time/token/attention measurement exists. Output replay verifies emitted data, not that a participant cognitively inspected every line or that no unmetered access occurred. All participants report no truncation. Launch provenance says the protocol and implementation packet were publicly frozen before the runs; this review verified local source/replay consistency, not remote publication chronology. The summary's unrelated classification is deliberately narrow and not an exhaustive measure of unnecessary reasoning.

Decision 0016 permits a concrete source walkthrough for a small reversible trial and does not require a larger benchmark to prove this idea. The frozen four-run stopping condition has been met. The appropriate result is to retain the successful overview route and the inconsistent/deeper/full-review outcomes together. There is no established reduction in correction risk, change obligations, full-review work or actual elapsed cost, and no evidence that overview-only work is frequent enough to outweigh the added surfaces in this repository. On the present comparison, this exact runtime relocation is not justified.

No further experiment or production gate should be run merely to seek adoption. A future concrete maintenance task demonstrating repeated coordinator-only benefit under ordinary search/range use, or a changed interface/cost context, could reopen value; it would need to be assessed on its own evidence rather than extrapolated from file lengths. If runtime adoption is later selected, fresh normal verification including PostgreSQL and independent Alder review remains required. That readiness requirement is separate from the current value conclusion.
