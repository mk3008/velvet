# Astraの保守要求：判断に必要な根拠へ到達できること

[PR #35の追加依頼](https://github.com/mk3008/velvet/pull/35#issuecomment-5671784799)への回答。
対象は `81ee496` 時点の既存評価と、このセッションで利用している道具。
これは保守主体としての要求・仮説の整理であり、採用済みのcoding ruleでも、新しい実験結果でもない。

私にとって保守しやすいリポジトリは、**変更について答えるべき問いから、その判断に必要な正本・実装・検証へ到達でき、確認済みの範囲と未確定の範囲を区別したまま作業を終えられるもの**である。
短いコード、少ないファイル、名前付きの関数は、そのために使える手段にすぎない。
特に欲しいのは「どこにあるか」と「そこまで見れば何を言えるか」の両方である。

これは内部認知の測定ではない。以下の「助かる」「困る」は、公開された読取経路・回答・作業上の制約から導いた自己評価である。
人間との優劣、Astra全般の性能、将来のツール環境へは一般化しない。

## 根拠の強さと現在の道具

- **観測 O**：既存の記録に現れた読取操作・回答・結果。読んだ内容への注意量や選択理由までログだけで確定しない。
- **現状 C**：このリポジトリや今回のツール契約から確認できる能力・制約。効果測定ではない。
- **仮説 H**：O/Cを材料にした保守要求、理由の推論、候補の期待効果。実装・障害対応・feature追加の比較実験は行っていない。

元の[B2比較](README.md)はfunction単位の取得を備え、任意rangeを提供しなかった。
[overview比較](overview/participant.md)はfile / range / regex search / file list / line countを提供したが、読取先をfeature内に限定した。
この違いを「Astraには関数ジャンプができない」と読み替えてはいけない。

通常のこの作業環境ではshellから `rg`、範囲取得、Gitのdiff/history、既存スクリプトを利用でき、GitHubからPR・CI結果を取得できる。
独立した既知の読取はまとめられるが、次の依存先を知るための読取は結果を待つ。
今回直接使っている操作には、IDE同等の意味解決済みsymbol jump / find references / call hierarchyは含まれていない。
検索は定義や参照の候補を返すが、同名・再export・動的SQLの意味的な完全性を保証しない。
一方、[parity実装](overview/parity.mjs)はTypeScriptの構文情報を既に利用している。構文境界を得ることと、完全な参照解決を提供することは別である。

出力量の上限も現実の制約である。この追補の確認中もコメント一覧に本文とHTMLをまとめて取得した出力が切れ、最新コメントの本文だけを取り直した。
これは今回の非計測の作業例であり、#33の試行数には加えない。overview試行では全員が切詰めなしと報告している。
行数削減より、必要情報を欠落なく取得したと確認できることが先に必要である。

## 保守活動ごとの要求

以下の要求と候補方向はすべてH。根拠欄でOとCを明示する。
「近い」は同じファイルという意味に限定せず、一度の取得や正確な参照で併せて確認できることを含む。

| 活動／欲しい情報 | なぜ必要だと考えるか | 満たし得る方向 | 反対コスト・適用限界 |
| --- | --- | --- | --- |
| 全体像・主要フロー：責務、dispatch、成功・失敗の出口と、今は保留できる詳細を知りたい | O2。r2は実際にworkerを保留できたがr4は裏付けを求めた。概要の存在と、概要だけで答えられる問いは別 | 既存のcoordinatorを直接取得し、委譲先と未確認事項を併記できる入口 | 要約を正本化すると陳腐化する。概要に全保証を詰めると詳細を複製する |
| 変更箇所・影響範囲：操作に名前があり、呼出元・状態・SQL・利用者まで必要な範囲を追いたい | O1の再取得差、Cの文字列検索。定義を見つけても全利用者を確認したことにはならない | symbol位置と参照候補の取得、意味名から関連テスト・SQLへの既存参照 | 細分化で公開面やhopが増える。検索結果ゼロは動的参照の不存在証明にならない |
| bug / incident：発生地点と、最初に破れた条件・永続化済みの状態を分けたい | O5ではDML後の検証とCOMMIT曖昧性を区別。実際のincident短縮は未測定 | エラーからRun、処理段階、SQL、回復所有者へ辿れる既存情報を一緒に確認 | 名前の明快さだけでは原因にならない。ログ追加なら機密・量・保守費用を別途評価する |
| invariant / ordering / transaction / recovery：局所処理の前提と後続効果、所有者を同時に確認したい | O5。mutable helperだけでは早期guard、Work、retirement、coordinatorを説明できない | 主張ごとにcaller、実行SQL、後続処理、回復を結ぶ証拠の取得 | 情報を全て同居させると別の問いには過剰。抽象化しても暗黙の状態依存が消えるわけではない |
| feature追加：既存の責務・拡張点・採用理由と、今回変えてよい意味を知りたい | C：[Business Design入口](../../docs/business-design/README.md)と[Decision入口](../../docs/decisions/README.md)は権限・意味を区別。追加実験はない | 現行正本から対象processと具体的な実装判断を辿り、似た既存例と照合 | 既存例のコピーは未承認の業務意味を承認しない。汎用拡張点を先に作る根拠にもならない |
| regression / test selection：どの主張をどの検証が支え、残る穴は何か知りたい | C：[既存検証](../../package.json)、[証拠CI](../../.github/workflows/issue-33-evaluation.yml)。O5の静的読解限界 | 変更した主張に既存テスト・実DB検証を対応させる短い作業記録 | 対応表の維持費、テスト名だけで十分と誤認する危険。局所選択で既存の必須gateを省略しない |
| diff / review・因果分離：意味の変更と移動・整形を区別して比較したい | C：今回のparityは宣言移動とruntime未変更を検査。レビュー速度の比較はない | 固定した基準版、目的の分かる差分、機械的な一致検査を必要な範囲で利用 | commitを細かくしても意味的独立は保証されない。構文一致はDB動作の証明ではない |
| rollback / reversibility：コードを戻せる範囲と、既に外へ出た効果を区別したい | O5と[Decision 0016](../../docs/decisions/0016-proportional-refactoring-decisions.md)。COMMIT失敗応答だけでrollbackを断言できない | 対象版・適用状態・不可逆なデータ効果と回復責務を判断の近くに置く | 一律のrollback手順書は不要な負担。コードrevertは既存データを元に戻さない |
| 正本の追跡：同じ語について仕様・実装上の判断・観測結果のどれを見ているか知りたい | C：Business Design入口は生成物やレビューを承認と区別。O5のpacketにはDB本体がなかった | 正本へのリンクと、未承認・未確認・履歴であることを明示する既存routing | 関連ファイルの列挙だけでは権威は決まらない。矛盾時にテストや新しい日付だけで業務意味を決めない |
| 後続作業での再利用：何を採用し、どの未確定事項なら再評価するかを回収したい | C：[候補記録](candidates.json)と0016はB2採用・A2保留・再開条件を保持。この追補でも過去結果を再利用 | 短い結論から対象版、根拠、限界、再開条件へ辿る | すべての作業を長文記録にすると入口が埋まる。版や前提が変われば過去の結論を再検証する |

ここで最も高コストと考えるのは、単にファイルを一つ余分に開くことより、**開いた先でも「この問いに答える証拠が揃ったか」を判定できず、依存先を増やし続ける状態**である。
O2/O3はその仮説と整合するが、理由や時間を直接測定してはいない。
逆に、重要な未確定事項が残るなら読取を止めないことが正しい。少ない取得数を成功条件にはしない。

## 共通性・ツール依存性・衝突

| 区分 | 要求と位置付け |
| --- | --- |
| 人間にもAIにも共通しそう | 正本、変更の因果、前後条件、責務、検証可能性、復旧範囲、過去判断の理由を辿れること。これは共通性の仮説で、人間比較の結果ではない |
| 今回のAstra＋道具に強く依存 | 取得可能なfile/range/name、切詰めの検出、正確な参照、意味検索を持たない場面での曖昧さ、結果待ちを伴う連続探索。読み直しには出力と照合が必要だが、attentionや記憶のコストは測っていない |
| 能力が変われば弱まる／逆転し得る | 正確なsymbol/reference取得なら、物理分割を使わず名前付き単位へ到達できる。自動依存展開ならhopの操作費は下がり、多ファイルが不利でなくなる可能性がある。大きい出力枠なら全読の取得費は下がる。いずれも意味判断や業務正本の必要性は残る |
| addressability ↔ hop cost | 名付けは指定と再取得を助け得るが、呼出元の前提と別の定義を繋ぐ必要を増やす。ファイル数や関数数の単独最適化では決まらない |
| 局所性 ↔ overview | 一緒に変わる情報が近いと照合しやすい。一方、全体像の問いでは詳細が過剰。課題に応じて取得単位を変えられることが候補要求 |
| 抽象化 ↔ hidden dependency | 委譲は本文を短くするが、引数以外の状態・transaction・stored SQLの契約が隠れると確認範囲が広がる。型や名称だけで効果を保証できない |
| 要約・索引 ↔ 二重管理 | 入口は探索を助け得るが、実装を言い直した別文書が古くなると誤判断の入口になる。参照中心の短い案内でも維持費はゼロではない |
| 局所検証 ↔ 見落とし | 対象の絞込みは反復を軽くするが、跨るinvariantやDB効果は広い検証を要する。正確なtest mappingを未検証の完全性保証にしない |

したがって「IDEがないなら全関数を別ファイルにする」は、今の要求から直ちには出てこない。
物理分割は住所を得る一手段だが、O1には取得道具の影響があり、O3では別ファイルでも詳細を広く読んだ。
人間のIDE利用習慣や一般的な可読性慣行を、この結論の根拠にはしていない。

## 次に価値がありそうな候補方向（未採用・未実装）

順位は現在の困りごとへの近さ、可逆性、既存情報の再利用からの推論であり、測定された優劣ではない。
ここでは三方向を提示して止める。全部の実施や新規Fresh Agent比較を予定しない。

1. **構造を変えず、意味単位の取得を改善する。**
   既存の名前・構文境界を使い、定義に必要なcallerや参照候補を取得する方向。
   原理は道具側のaddressability。O1のreader依存とO3の全worker取得に直接対応する。
   次に試すなら一つの実際の狭い保守課題で通常range/searchと比べ、必要な前後条件を落とさず、繰返し取得や曖昧な検索が減るかを見る。
   parser依存、TS/SQLを跨ぐ参照、動的依存の取りこぼしが反対コスト。通常rangeで十分なら作らない／止める。
   既存function-readerを本番ツールへ昇格させる決定ではなく、道具と構造の効果を分ける候補である。
2. **問いから正本・実装・検証へ繋ぐ短い証拠経路。**
   例えば「mutable identityはどの時点で守られるか」からBusiness Design、早期guard、receipt、DB処理、該当テストへ既存リンクを辿れるかを確認する方向。
   原理はファイル分割ではなく、異種情報間の意味と根拠の追跡。
   次の関連修正で一つの主張に限定し、既存routingで足りるなら追加しない。足りなければ最小の参照を候補とする。
   効果の観点は「根拠や未確認を取り違えないか」。二重仕様化・陳腐化・リンク維持が費用であり、完全なtraceability台帳は提案しない。
3. **本当に別々に変更・検証する責務だけ境界候補にする。**
   原理は探索操作の短縮ではなく、変更の波及と検証義務の隔離。
   将来の実際の変更で、共有する状態や回復の責務を残したまま、無関係な変更・fixtureを避けられるかを具体的に比べる。
   interface、重複、transaction所有者の分散が増えるなら見送る。
   現在はその利益を示す新しい変更事例がなく、順位を下げる。A2の既存の未確定事項を解消したことにはならない。

一つの短い入口だけでなく、取得能力、根拠の接続、変更責務という異なる原理から候補を考える。
その際も「短く見える」ことと「安全な判断に必要な作業が減る」ことを分ける。

## 今回の完了範囲

既存ログと回答、reader課題、独立レビュー、正本routing、検証入口を読み、要求と根拠の対応を整理した。
外部の一般論を裏付けとして追加していない。新しい候補実装、Fresh Agent実験、保守時間・事故率の測定は行っていない。
この文章自体は著者による整理であり、既存の独立レビューがこの追補まで承認したものではない。

B2採用、A2保留、今回の3ファイル案を採用しない判断、value / timing / evidence effortの区別を維持する。
ここに挙げた欲求を新しいAGENTS規則や必須文書へ変換しない。次の採否は別の判断である。
今回の差分はこの報告と既存report/Decisionからの案内のみ。リンク・記録数値・差分範囲を確認し、PR上の既存CI結果を併記する。
CIの成功はこの自己評価や候補順位の有効性を検証するものではない。
