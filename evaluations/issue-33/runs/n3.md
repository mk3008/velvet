## Execution outline (outline phase)

`executeRowTransfer` (208–514) fetches pending items using bounded or unbounded pending SQL (233–241). Before reading source current values, it resolves each pending logical key from a frozen copy, validates its column names, calls `projection`, and stores its textual identity (242–249). It executes the stored source SQL only if work exists, requires an array of rows, and builds a current-row map, rejecting duplicate logical keys (250–260). It initializes counters and a completed-context set (261–263).

For each item (264–512):

1. Resolve link/model and current row; detect a duplicate link/key context, otherwise fetch Active; map source fields while rejecting missing/undefined mapped values (265–287).
2. Determine initial no-op eligibility. For an active row with source data outside insert-only mode, check mutable mapped identity first, validate comparison exclusions and reassessment SQL/binding, run reassessment, then compare its returned JSON texts to decide no-op (288–336).
3. Choose duplicate/no-op skip status, construct Work and result fields, and record Work (or routine skipped metadata) before destination execution (337–380).
4. For non-skips, execute mutable update/delete against Active, check returned cardinality and destination identity, then retire Active on delete (381–418). For immutable Active, execute Red transfer, validate cardinality and a different returned identity, then retire Active and record Red lineage (419–456). When a source row exists and the route needs insertion, execute stored insert, validate mapping consumption, cardinality and expected destination key, then record Active/lineage or combined routine metadata, and increment inserted (457–508).
5. Count skips, mark the context completed, and record processing unless an earlier combined metadata call already did so (509–511).

Return `{ inserted, skipped }` (513). The counts concern inserts and skips; mutable updates/deletes are not incremented here.

## Mutable UPDATE/DELETE returned-key locator (locator phase)

The returned-key guard is directly in `executeRowTransfer`, lines 401–407, inside `if (!skip)` (381) and `if (active && mutable)` (382). The statement is selected from `generated_update_transfer_sql_body` or `generated_delete_transfer_sql_body` according to source-row presence (383–386). After statement/binding checks, destination SQL executes at 398. Cardinality is checked first at 399–400: both `result.rows?.length` and `result.rowCount` must equal one. Then `isDeepStrictEqual(projection(result.rows[0], link.destination_key_columns), active.destination_key_json)` must succeed; otherwise line 407 throws an operation-specific destination-key mismatch error. `projection` (62–70) selects every requested key column and throws for a missing own property, undefined, or null value (65–66).

Ordering is explicit:

- With an Active and current source row, reassessment and `queries.compareSql` run at 309–335 before Work and before mutable destination SQL. A delete has no current row and bypasses the reassessment block guarded at 289.
- Work fields are constructed at 346–358, then `queries.workSql` is awaited at 374–379 before destination SQL and returned-key validation. The routine skipped metadata alternative applies only to skips, so a real mutable update/delete uses `workSql` even in routine mode.
- Returned-key validation follows destination execution and cardinality checking and precedes delete retirement (408–417). On routine delete, retirement calls `queries.retireMetadataSql` with `withLineage: false` (409–413). Otherwise it calls `retireRowActive` (415). That helper first awaits `queries.releaseActiveReferencesSql` (522–525), then `queries.activeDeleteSql` (526–529), and requires exactly one returned removal row (530). A mutable update does not retire Active here.
- Completion marking and processing recording occur later at 510–511. A returned-key failure therefore throws before delete retirement and that processing call, although the destination SQL and Work query have already executed; durable effects depend on transaction behavior not inspected here.

The distinct earlier identity check that must stay earlier is at 291–298: for mutable Active with a current row, compare `projection(mapped, link.destination_key_columns)` with `active.destination_key_json`. It checks the proposed mapped identity before comparison exclusions, reassessment, no-op selection, and Work recording. This ensures key drift is rejected even when key columns are excluded from comparison or reassessment would otherwise classify the item as a no-op. It cannot be replaced by the later returned-key guard because a skipped item never executes that guard. Also, the pre-loop logical identity validation (242–249) explicitly precedes source-current-value retrieval (250–253).
