## Locator answer (locator phase)

Mutable UPDATE/DELETE returned-key validation lives in `executeMutableDestination` (492–524), called and awaited by `executeRowTransfer` at 382–383 only for an unskipped active mutable destination. Presence of the current source `row` selects Black Update / `generated_update_transfer_sql_body`; absence selects Physical Delete / `generated_delete_transfer_sql_body` (499–502).

The helper validates stored SQL and binding requirements (503–513), executes the destination statement (514), requires exactly one returned row and exactly one affected row (515–516), then projects the returned destination key and compares it using `isDeepStrictEqual` to `active.destination_key_json` (517–523). This last block is the mutable returned-key check. `projection` (62–70) rejects missing, undefined and null key components, so those also fail before equality can succeed.

Ordering:

- For updates, reassessment and its comparison decision already completed at 309–335, before Work recording and before the helper call. A reassessment no-op skips the destination helper entirely. For deletes there is no current row, so the active/current-row reassessment block at 289 is bypassed.
- Work is recorded at 374–379, before the mutable call at 383 and therefore before both destination execution and returned-key validation. Non-skipped mutable operations use `queries.workSql`, including in routine mode.
- The awaited helper must return successfully before source-absent mutable retirement at 384–393. Routine retirement calls `queries.retireMetadataSql` with `withLineage: false` (386–389). Nonroutine retirement calls `retireRowActive` (391), which releases references (532–535), deletes Active Black (536–539), and requires one removed row (540). A returned-key failure throws before any of these subsequent retirement calls. Updates do not enter this retirement block.
- Successful completion then marks the context completed and writes Processing at 486–487; a helper failure prevents those subsequent steps in this invocation.

The earlier identity check that must stay earlier is the mutable mapped-key vs. Active Black equality check in `executeRowTransfer` at 290–298. It compares `projection(mapped, link.destination_key_columns)` against `active.destination_key_json` whenever active and current rows exist for mutable work. It precedes reassessment, exclusion-based comparison and no-op determination. It must occur there to reject a changed mutable identity even if key columns are excluded from comparison or reassessment would otherwise produce a no-op, bypassing the destination helper. This is distinct from checking the key actually returned after UPDATE/DELETE.
