# Candidate rule v1 — observable change boundaries

Frozen before independent application and implementation (baseline b3190e3d341ee21478161f2b8b31f96826c503b1).
This is an evaluation procedure, not a required architecture or size threshold.

1. Inspect current Business Design, relevant decisions, implementation, tests, and meaningful historical patches. List actual independent reasons to change, with source anchors; do not count mechanical renames as separate reasons.
2. Consider refactoring when distinct observed reasons share an implementation unit AND a concrete maintenance task exposes unrelated logic, duplicated invariant decisions, or dispersed coordinated edits. LOC alone cannot trigger action. State a counterexample where keeping the unit is better.
3. Compare keep, a local extraction/reorganization, and (only if justified) wider alternatives. Predict relevant edit locations AND additional interfaces/inspection hops for representative tasks. Prefer keeping shared ordering and transaction/failure ownership explicit. Splitting one invariant across owners is a cost, even if files shrink.
4. Keep when evidence is speculative, one cohesive algorithm changes together, the existing seam is sufficient, or the candidate only relocates complexity without reducing unrelated reasoning. Record what future observation would reopen the decision.
5. Automatically implement on a dedicated branch only when current meanings/public contracts remain unchanged, dependencies and invariant ownership are explicit, the edit is reversible and scoped, and relevant regression gates can run. Automatic means implementation for review, not merge. Missing evidence, disproportionate risk, or insufficient regression coverage means proposal/recorded concern. Ask the owner only for unresolved business requirements, external effects/costs or scope expansion; do not ask them to choose filenames.
6. Define comparison and stop criteria before changing code. Require demonstrated task-specific locality/inspection benefit, no materially worse shared-invariant ownership or edit dispersion, and required regression checks. If benefits are mixed, narrow the claim or keep/propose; do not optimize indefinitely.
7. Record inputs/revisions, observed reasons, alternatives, invariant owner map, action and confidence, expected/measured benefits and costs, verification and reopening condition. Label engineering precedent, repository evidence, and agent judgment separately. After ordinary feature work, reconsider only newly observed evidence or a reopened concern, not every file by size.
