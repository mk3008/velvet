These local CHECKs protect durable interpretation even for direct SQL writes; they are not justified merely because the public API already avoids invalid states:

- Work route is either `skipped` or its captured model. Red requires immutable; UPDATE/DELETE require mutable. Black INSERT/UPDATE require source existence; DELETE requires absence. INSERT and UPDATE cannot both be required. Existing skip consistency still applies. This does **not** reimplement source comparison or all historical-state combinations.
- Final Processing maps skipped to `no_op`/`duplicate_ignore`, succeeded to an operation result. `failed` retains all existing enum results and nullable `error_message`: current work failure rolls metadata back and records failure on Run, so inventing per-item failure diagnostics would define a new policy. Non-null diagnostics on success are not newly prohibited either; error text is not the finality discriminator.
- Lineage Black uses `transfer_source`; Red uses `reversed_destination_row`. The source key therefore has an unambiguous kind, without pretending the CHECK proves its actual value.

Still-admissible wrong source keys/hashes, Red without a historical evaluated key, Processing inconsistent with Work flags, or manually fabricated Active/Lineage records are explicit limits. They require cross-row/external truth or a broader complete-decision contract. Retain application validation, atomic writes and deployment review; do not grow a second execution engine in CHECKs/triggers.

## Duplication and keys

Context IDs copied into Work/Processing/Lineage are useful for tracing and query access. Composite unique keys containing a surrogate PK are mathematically redundant for uniqueness, but required as PostgreSQL targets for the current multi-column FKs. Those FKs add _context agreement_, unlike independent single-column FKs.

Several independent FKs are logically redundant once the contextual FK/path exists: e.g. Work's Run/Setting/Link/Active references, Processing's individual context references and its Run/Setting and Setting/Link FKs beneath its complete Work FK; Lineage's individual Run/Setting/Link references beneath its context FKs. They are not additional business invariants. Keep them in this change: removing them adds migration and relationship/metadata surface without a demonstrated current correctness or resource problem. No new redundant FK/index is added, and no claim that all existing physical constraints are indispensable is made. Supporting indexes are useful access choices, not business mandates; no performance tuning is attempted here.

Dirty physical JSON and resolved logical JSON are different identities. Work holds evaluation context; Active holds a current pointer; Lineage Red holds an old **destination** key. These cannot be normalized into one universal source-key row. Processing's logical key/hash duplicates Work exactly in current writers; it is useful self-contained inspection/search evidence, not independent truth. Keep the current shape; a separate dictionary or JSON-inclusive FK costs more machinery than the current atomic writers justify. Hashes are lookup/trace aids; JSON keys and context own identity. Hashes alone are never identity uniqueness constraints.

`active_black_id` plus `evaluated_destination_key_json` is deliberate current/history separation (Decision 0003). Retirement clears **all** historical live references before deleting Active, preserving the old destination key. Keeping retired Active rows merely to support a FK would turn a current-state index into another history lifecycle. Removing the evaluation snapshot would lose the original target. Neither is an improvement.

## The four set-phase columns

Keep all four nullable JSONB columns and migration 0025 unchanged.

| Column                                        | Ownership and lifecycle                                                                                                                           | DB versus application                                                                                                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setting.set_phase_definition`                | Source/dirty identity, source SQL digest, independent-key assertion and admission cap. Sole dispatch opt-in: SQL NULL selects row/routine.        | DB enforces object when non-null. Runtime validates version/revision, full statement hashes, key contract and bounded profile. Empty/invalid object is explicit opt-in failure, not fallback. |
| `destination_link.set_phase_definition`       | Mapping-specific evaluation and Black INSERT. May remain after Setting is disabled; does not independently select the executor.                   | Validate enabled Links under the Setting lock. Incomplete explicit opt-in fails closed. Disabled Links need not be execution-ready.                                                           |
| `destination_definition.set_phase_definition` | Red projection/INSERT and actual destination verification, reusable across Links. These consume phase input but must not redefine source mapping. | Versioned SQL/input/output validation and authored semantics belong to deployment/runtime. Shared object is loaded in each relevant Link context.                                             |
| `run.execution_configuration`                 | Snapshot of the selected locked master rows, exact SQL and hash/revision for that Run. Row/routine Run keeps NULL.                                | Object CHECK only. Boundary captures evidence when creating Run and re-locks/re-reads exact selected configuration before work; mismatch fails the persisted Run.                             |

Administrative enablement installs the complete enabled profile transactionally. The DB permits Setting-only opt-in or stale Link/Destination objects, but none is silently executed through the legacy fallback. Disabling only Setting preserves legacy SQL and leaves the other definitions inert; it does not require deleting reusable Destination configuration. The current exclusive, versioned object has no independent relational identity/lifecycle needing a new table. A normalized phase registry, JSON Schema CHECK implementation, DB-enforced cross-master completeness, or future mutable/insert-only phase generalization is unjustified.

SQL NULL and JSON `null` differ: the latter fails the existing object CHECK. Runtime support restrictions (v1 immutable, flat text keys, no date hook, authored independence) are versioned execution limits, not universal schema rules. Schema should still represent legacy composite/numeric keys and other models.

## Provenance and Run evidence

`setting.source_sql_body` remains the canonical full source. Registration computes `source_sql_hash` as SHA-256 over its exact text for metadata/change detection. `set_phase_definition.sourceSqlSha256` is the independently installed profile's _expected digest_ for that same body. The algorithm is not different. A profile can become stale when the body changes, so runtime compares the body to the expected digest, not two asserted hashes to each other. The existing metadata hash can be stale after privileged direct editing and is not used as an authorization gate. Keep both roles; document the distinction rather than claim two SQL sources of truth or build an approval registry.

Link/Destination JSON stores exact text, digest and revision together. Updating text without digest is rejected; editing both remains possible for a privileged administrator. Hash/revision is deployment provenance, not semantic approval, tamper-proof evidence or Serene source identity. Trusted SQL content, actual Red reversal and truthful verification queries still require review. Runtime additionally checks cardinalities, keys, actual INSERT command/count and receipts.

Full Run evidence duplicates mutable master data intentionally. FK + revision/hash alone cannot reconstruct deleted/overwritten SQL because no immutable version registry exists. One snapshot per Run supplies configuration provenance for incident investigation; it does not snapshot source/destination data, function bodies, triggers or the whole database and therefore does **not** promise replay/reproducibility of results. It also does not make Run a SQL authoring/configuration owner: execution reads masters, not past Run evidence. A failed Run after the exact reread disagrees retains the attempted configuration, not proof those statements executed.

Cost is proportional to selected configuration text per Run, not per Dirty Key; shared Destination fields are repeated per selected Link in the existing evidence object. This is real duplication but bounded by the configured Link set, with no measured storage requirement justifying a separate registry or compressed reference format here. Row/routine's NULL is an explicit evidence asymmetry, not equivalent historical SQL reconstruction. No legacy history rewrite is proposed.

## Migration and verification

Apply migrations once in ascending filename order: `0025-set-phase.sql`, then `0026-schema-invariants.sql`. Migration numbers represent application order. The initially proposed Issue-number filename `0018` was rejected in the owner review: ordinary file ordering must give the correct operation order without remembering an exception. New databases use canonical DDL. The transaction validates all existing rows immediately and aborts all four additions if any contradict them. It neither backfills nor deletes history. Investigate a reported constraint violation against actual history before deciding any repair; do not rewrite business evidence automatically. CHECK validation scans/locks the affected metadata tables; schedule installation accordingly rather than claim an online migration.

Direct PostgreSQL tests in `tests/adapters/pg/schema-invariants.integration.test.ts` cover accepted routes/skips/retired references, rejected INSERT and UPDATE combinations, optional Work on Lineage, preserved failed Processing states, and populated upgrade failure/rollback/success plus canonical CHECK equivalence. Existing Phase 1–5, row/routine and set-phase differential/history, invalid opt-in, existing-history enablement, rollback and COMMIT-response-loss suites remain regression gates.
